# P4.1 — Authorization Hardening

- Date: 2026-09-28
- Baseline: `p4-security-clinical-pilot-audit` at `87bd1a8`
- Branch: `p4.1-authorization-hardening`
- Scope: P4-007 and P4-008 only

## 1. Initial state

The existing roles are `patient`, `staff` and `clinic_admin`; staff subroles are `doctor`, `nurse` and `admin`. Tenant checks already prevented most cross-clinic lookups, but same-clinic membership was incorrectly sufficient for administrative access to consent history, full demographics and appointment reasons. Consent grant/revoke was also available to every non-patient role.

The pre-existing uncommitted development-only `docker-compose.yml` port change (`5432` to `5433`) was preserved and excluded from P4.1 commits.

## 2. Minimum-access authorization matrix

| Resource / operation | Patient | Doctor / nurse | Administrative staff | Clinic admin |
|---|---|---|---|---|
| Patient directory | denied | basic operational identity, same clinic | basic operational identity, same clinic | basic operational identity, same clinic |
| Full demographics | own record | read, same clinic | denied | denied |
| Change phone | own record | same clinic | denied | denied |
| Change birth date / health number | denied | same clinic | denied | denied |
| Deactivate patient | denied | denied | denied | same clinic; summary response only |
| Consent list / detail | own | read, same clinic | denied | denied |
| Consent grant / revoke | own only | denied | denied | denied |
| Consent update | no endpoint | no endpoint | no endpoint | no endpoint |
| Appointment operational fields | own read | same-clinic read/write | same-clinic read/write | same-clinic read/write |
| Appointment reason | own read | same-clinic read/write | omitted from responses; write denied | omitted from responses; write denied |

Consent mutation is intentionally patient-only. P4.1 does not introduce a witness, proxy or clinician-on-behalf-of-patient workflow without an approved clinical/legal model.

## 3. Problems found

1. Consent services special-cased patients but treated every non-patient in the clinic as authorized.
2. Patient list, detail, update and deactivation responses reused a full demographic schema.
3. Appointment responses always serialized `reason`, and administrative roles could submit it on create/update.
4. The frontend displayed sensitive directory columns and offered consent/reason actions to administrative users.
5. Request schemas already rejected unknown fields, but field-level patient update authorization was missing.

## 4. Changes made

- Centralized recognition of clinical staff as doctor/nurse.
- Applied clinical patient access to consent reads and patient full-detail reads.
- Restricted consent grant/revoke to the authenticated patient who owns the record.
- Added a `PatientSummary` response containing only ID, clinic ID, name and active state.
- Changed the directory and administrative deactivation response to the summary schema.
- Restricted full demographic updates to doctor/nurse; patients may update only their own phone.
- Redacted appointment `reason` to `null` for administrative roles and rejected administrative reason writes with 403.
- Preserved operational appointment scheduling, rescheduling and cancellation for administrative roles.
- Preserved 404 non-disclosure for cross-tenant resources, including reason-write probes.
- Updated the frontend to consume summary rows and hide actions/fields not allowed by the backend.

## 5. Tests added and updated

`test_authorization_p4_1.py` creates two clinics, each with a patient, doctor, nurse, administrative staff member and clinic admin. It proves positive and negative paths for consent, demographics, mass assignment, appointment reasons and cross-tenant access.

Explicit negative coverage includes:

- administrative consent list/detail/grant/revoke: 403;
- doctor/nurse consent mutation: 403;
- administrative full-demographic read/update: 403;
- patient sensitive-demographic update: 403;
- `clinic_id`, `user_id` and unknown patient fields: 422;
- administrative reason create/update: 403;
- cross-tenant patient, consent and appointment access/write probes: 404;
- administrative directory/deactivation responses: summary fields only.

## 7. IDOR validation

Every role in clinic B was tested against clinic A patient details, consent collection/detail and appointment detail. All returned 404. Authenticated write probes against clinic A appointment reasons from clinic B also returned 404, preserving non-disclosure before role denial.

## 8. RBAC validation

Authorization is enforced by backend service/router checks. Frontend guards are UX-only. Same-clinic membership no longer implies clinical access. Patient update schemas continue to reject extra fields, and the service adds a per-role field allowlist.

## 9. Consent authorization

Before P4.1, every non-patient same-clinic user could list, read, grant and revoke. After P4.1, patients list/read/grant/revoke only their own consents; doctors and nurses may list/read same-clinic consents; administrative staff and clinic admins have no consent access. No role can update a consent because no update endpoint exists.

## 10. Patient data authorization

Administrative roles receive only operational identity from the directory and deactivation response. They cannot retrieve or patch the full patient resource. Patients read their own full record and can change only their phone. Doctors and nurses can read and change the supported demographic fields for same-clinic patients.

## 11. Appointment reason authorization

Patients see reasons on their own appointments. Doctors and nurses see and write reasons for same-clinic appointments. Administrative staff and clinic admins retain operational scheduling access, but `reason` is returned as `null` and any attempt to submit it is rejected with 403.

## 12. Remaining risks

P4.1 does not resolve external or separately scoped requirements: production TLS/domain, managed secret storage and rotation, encrypted/immutable off-site backups with restore evidence, staffed alert destination, shared rate-limit storage for multi-replica use, MFA, verified password recovery, DPIA/privacy/legal approval, retention/deletion policy, approved invitation delivery, incident/support procedures, account reactivation/role-change workflow and additional database-level tenant constraints.

The four low Bandit findings are unchanged P4 informational results: two runtime assertions, one invitation-router assertion pair and a false-positive audit enum value named `password_change`. No medium/high finding was reported.

## 13. P4 blocker status

- **P4-007 / Blocker 1 — Consent authority: CLOSED.** The patient owns grant/revoke authority; doctor/nurse read is explicit; administrative access is denied. Covered by positive, negative and cross-tenant tests.
- **P4-008 / Blocker 2 — Administrative clinical-data access: CLOSED.** Administrative roles receive operational patient/appointment data only, cannot access full demographics, and cannot read/write appointment reasons. Covered by response-shape, 403, mass-assignment and cross-tenant tests.

No new P0/P1 application-security blocker was found in the P4.1 scope.

## 14. Technical Pilot Gate

**TECHNICALLY READY FOR CONTROLLED PILOT: YES**

This is a code-level authorization gate for a private controlled pilot, not authorization for public deployment or clinical launch. The external infrastructure, legal/privacy and operational items in section 12 remain mandatory and unresolved.
